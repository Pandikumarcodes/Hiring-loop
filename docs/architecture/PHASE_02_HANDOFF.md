# Phase 02 — Database Foundation Handoff

## Status

COMPLETE

## Objective

Establish the PostgreSQL/Prisma database foundation, migration discipline,
isolated development and test databases, tenant-foundation constraints, and a
verified database client boundary without implementing product features.

## Completed Work

- Prisma 7.10.0 and PostgreSQL were configured for the JavaScript ES-module backend.
- A reusable Prisma client using `PrismaPg` was established.
- The initial tenant foundation schema and migration were created and verified.
- `hiringloop_dev` and `hiringloop_test` use the same migration history.
- Database integration tests cover relationships, constraints, UUIDv7, timestamps,
  restrictive deletes, and the global-user/multi-organization invariant.

## Database Architecture

PostgreSQL is the authoritative source of truth. The backend uses Node.js,
Express.js, JavaScript, ES modules, Prisma 7.10.0, `pg`, and
`@prisma/adapter-pg`. Feature-specific physical entities remain deferred to
their later roadmap phases.

## Implemented Schema

Only these physical models exist:

- `User`: global identity with application-supplied UUIDv7 ID.
- `Organization`: tenant root with application-supplied UUIDv7 ID and required name.
- `OrganizationMembership`: first-class relationship with application-supplied
  UUIDv7 ID, organization, user, role, and timestamps.

Future entities including invitations, jobs, pipelines, candidates,
applications, interviews, scorecards, communications, offers, talent pools,
activity, audit logs, integrations, and AI-specific models are intentionally
deferred.

## Relationships

`User` has many `OrganizationMembership` records. `Organization` has many
`OrganizationMembership` records. Each Membership belongs to exactly one User
and one Organization. User is global; Membership establishes tenant context;
User is not tenant-owned directly.

## Constraints

- `OrganizationMembership_organizationId_userId_key` enforces uniqueness per
  organization/user pair.
- `OrganizationMembership_role_check` allows only `ADMIN`, `RECRUITER`,
  `HIRING_MANAGER`, and `INTERVIEWER`.
- Membership `userId` references `User.id`.
- Membership `organizationId` references `Organization.id`.
- Both foreign keys use `ON DELETE RESTRICT ON UPDATE RESTRICT`.
- No Role or Permission tables and no broad cascade behavior were introduced.

## Migration History

The first migration is `20260901105250_init_tenant_foundation`. It creates only
the three foundation tables, their structural indexes, restrictive foreign
keys, timestamp columns, and the reviewed PostgreSQL role CHECK constraint.
The migration is present in the repository migration history and is applied to
both `hiringloop_dev` and `hiringloop_test`; both databases reported current
migration status.

## Prisma Architecture

One reusable Prisma client is created per process with `PrismaPg`; it is not
created per request. Connect/disconnect lifecycle handling remains at the
server boundary, while `app.js` remains independently testable. Later
repositories will consume this database boundary; controllers must not access
Prisma directly.

The intended application flow is:

```text
Route → Middleware → Controller → Service / Use Case
      → Repository / Data Access → Prisma → PostgreSQL
```

## UUID Strategy

Entity IDs are generated by the application with `uuid.v7()` from `uuid`.
There is no UUIDv4 fallback and no Prisma/database UUID default for the current
entities. UUIDv7 database round-trip behavior is covered by integration tests.

## Timestamp Strategy

Created and updated timestamps use PostgreSQL `timestamptz(6)` for UTC instant
semantics. `createdAt` has a database `CURRENT_TIMESTAMP` default. `updatedAt`
is maintained consistently by Prisma through `@updatedAt`.

## Development / Test Database Model

- Development uses `DATABASE_URL` targeting `hiringloop_dev`.
- Integration tests use `TEST_DATABASE_URL` targeting `hiringloop_test`.
- Test tooling requires `TEST_DATABASE_URL`, validates the exact test database
  name, and never falls back to `DATABASE_URL`.
- Credentials are environment-owned and are not logged or documented.
- Existing migrations are applied to the test database with `prisma migrate deploy`.

## Test Coverage

The isolated database suite reports 7/7 passing tests and proves:

- basic User/Organization/Membership relationship and relation queries;
- duplicate Membership rejection;
- one User belonging to multiple Organizations;
- PostgreSQL role CHECK rejection;
- invalid User and Organization foreign-key rejection;
- restrictive User and Organization deletes;
- UUIDv7 round-trip and timestamp persistence;
- User has no `organizationId`.

Fixtures use generated UUIDv7 IDs, FK-safe cleanup in `finally` blocks, a
reusable integration client, and suite disconnect. No test rows remain after
execution. Unit tests report 2/2 passing.

## Security Decisions

Organization is the tenant root and User is global identity. Frontend-provided
organization IDs are never authorization authority. Future repositories must
use verified tenant context. Database constraints provide structural integrity
but do not replace backend authentication or authorization. Restrictive FKs
prevent destructive historical cascades. `.env` remains ignored and secrets
remain environment-owned.

## Performance Decisions

No Redis or caching was introduced. The schema is not speculatively indexed;
indexes are limited to primary keys, membership uniqueness, and the justified
User-first membership lookup. UUIDv7 provides reasonable index locality. Future
indexes require feature-specific query evidence and later `EXPLAIN ANALYZE`
review.

## Reliability / Transaction Foundations

The foundation assumes PostgreSQL READ COMMITTED, short transactions,
optimistic concurrency where appropriate, unique constraints as final race
guards, and bounded retries only for safe conflict classes. External S3,
email, and calendar work remains outside database transactions. Idempotency,
activity/audit transaction requirements, and feature-specific workflows remain
future implementation concerns.
